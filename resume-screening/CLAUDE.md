# 简历筛选

> 下面的“三点取两点”、岗位偏好和沟通清单来自一套招聘实践，岗位与人物已替换为虚构示例。它们用于演示如何记录和使用招聘口径，不是所有团队的默认标准。

## 选择岗位和评估口径

先看本次任务指定的岗位、用户提供的 JD 和 `jobs/` 中已有的岗位。`example: true` 表示示例岗位。

- **试跑示例**：使用示例岗位和本文件的示例口径，输出中标明是演示。
- **正式筛选**：使用真实 JD 和用户已确认的口径。用户已提供足够材料时直接开始；没有真实岗位时，先补充所需 JD，不把示例岗位代入。
- **尚未确定目标岗位**：可以先提取候选人经历和技术方向，岗位匹配结论待 JD 明确后补充。

需要建立岗位库时，按缺失信息补充，不重复询问已有内容：

1. 确认需要建立哪些真实岗位。
2. 补充岗位信息：
   - **岗位信息**：岗位名称、核心职责和 JD；已有文档时直接读取
   - **硬门槛**：每个岗位有没有一票否决项（学历/年限/特定经验）？
   - **用人经理偏好**：已确认的背景要求和沟通重点；没有就标注“待对齐”
   - **评分口径**：使用用户已有标准；“三点取两点”可作为参考，经用户采用后再用于真实筛选
3. 把访谈结果写成 `jobs/JOB-xxx_岗位名.md`（frontmatter 不带 `example`），并改写本文件的「岗位偏好」段为用户的真实口径
4. 示例 JD 可保留，正式筛选时排除 `example: true` 的文件。后续更新偏好时记录日期，并说明替换了哪条旧要求，避免新旧口径同时生效。

## 日常触发

用户要求筛选简历，或在明确的筛选上下文中提供 PDF 时：

- 指定岗位时读取该岗位及偏好；要求全库匹配时读取全部有效岗位。示例和正式筛选按上一节选择。
- PDF 按 [读取路径](../docs/pdf-reading.md) 处理。在根目录执行 `./run pdf "简历路径.pdf"`，检查 `report.json`、全文和每页 PNG；扫描或混合页面由脚本逐页尝试 OCR。退出码 3 表示仍有未解决页面，不能把局部提取当作完整阅读。
- 按下方流程提取经历、匹配岗位并给出依据。仅需某个环节时按用户要求输出。
- 文件名可能带招聘平台岗位水印，不把它当作候选人的实际经历或求职意向。与本次判断无关时无需讨论文件名。
- 区分“简历未提供”“自述待核验”和“已确认不符合”。缺少描述不能直接写成没有相关经历；候选人意愿和薪资预期也不从任职时长推断。

## 岗位偏好（来自与用人经理的对齐，示例数据）

**通用偏好：**

- "三点取两点"原则：经验匹配 / 年轻高潜 / 学历，具备两点才推
- 优先来源：一线大厂核心 infra 团队、头部大模型创业公司。其他团队的来源偏好按各自已确认的要求记录。
- 按本示例评分，达到两点才推荐；边界情况先核实关键缺口。
- **训练框架（JOB-101 陈默）、推理引擎（JOB-102 林澈）、RL 系统（JOB-104 沈一舟）更关注底层系统经验**：核对具体项目，而不只看 Megatron、GRPO、CUDA、Triton、vLLM 等关键词。重点看本人实现或修改了什么、承担什么角色、问题难度、规模和结果。后端开发或框架调用经验单独记录，不算作训推系统底层研发。

**训练框架岗 JOB-101（陈默，2026-06-02 示例口径）：**

- **岗位边界：只看大模型预训练 infra。** 纯推理/在线服务、纯后训练或 RL、通用 ML 平台、搜广推训练平台都不能仅凭技术栈相似判为直接匹配；有混合经历时，只计算其中可核实的预训练工作
- **需求拆为四个方向，先标方向再判断强弱：**
  1. **P0｜算子开发**：为预训练开发或深度优化 CUDA Kernel/通信算子，能说明具体算子、瓶颈、实现方式和收益。PyTorch 自定义算子、Triton/CUTLASS、Nsight profiling、算子融合是有效证据；"使用过 CUDA/NCCL"不算
     - **深度要求**：关注 attention 或通信算子、多个算子或跨版本的持续投入，以及端到端收益。本示例中，单个标准融合算子且端到端收益为 1-2% 时，先记为补充证据，不单独列为主、次方向；这一范围不作为其他团队的通用阈值。
  2. **P0｜训练稳定性**：实际定位过 Loss/Grad/NaN/Inf、通信 hang/straggler、OOM、Checkpoint 或性能回退等问题。优先 infra 人；算法背景只有在明确承担底层定位和系统修复时才计入
  3. **P1｜多模训练**：做过多模态模型预训练系统落地，解决过长序列、变长数据、并行切分、负载不均等训练问题；仅做多模态算法不算
  4. **P1｜主训**：实际设计/优化 DP、TP、PP、SP、EP/MoE、ZeRO/FSDP 等并行与内存策略，或承担规模扩展、训练吞吐和端到端运行保障
- **主/次方向怎么排：** 主方向取证据最深者，与 P0/P1 优先级无关；若最深的落在 P1，要在结论里显式说明 P0 两个方向的覆盖情况，供用人经理判断。方向最多标 1 主 + 1 次，其余有证据但不够深的降级为"补充证据"
- **深度判断：** 一人做过多个方向可以推，但至少一个方向必须有持续、主导且可验证的深度；框架名和并行策略名只作为检索词，不能代替项目证据
- **规模与结果证据：** 优先看训练参数/卡规模、吞吐或 MFU、显存节省、稳定运行时长等前后对比。千卡以上全流程经验是强加分，但不是简历未写即淘汰的硬门槛，pre-talk 核实
- **人选判断：** "资深"指能力和积累深，不设机械的最低年限；推荐前确认候选人本人愿意继续做预训练，避免预训练/后训练意向错配

**推理引擎岗 JOB-102（林澈，分档示例）：**

- 分 **Junior（1-3 年）** 和 **Senior（5 年+）** 两档，标准不同：
  - Junior：看潜力和基本功——CUDA/C++ 扎实、对 vLLM/SGLang 源码级熟悉即可，项目可以是参与
  - Senior：必须主导过生产级推理系统——PD 分离、KV Cache 优化、量化部署，要有量化收益数据
- 两档都要，推荐时明确标注档位

**ML 平台岗 JOB-103（吴桐，可迁移背景示例）：**

- 可考虑从相邻方向转入：有平台经验（调度、容器、搜广推数据平台），满足本示例的学历要求，且愿意做平台，可推荐进一步沟通
- 吴桐非常看重第一学历，这是硬门槛
- 需要稳重型人选（频繁跳槽、履历不连贯的慎推）
- 云原生方向的经验可迁移，具体核对调度、容器和平台开发项目
- 沟通角度，按岗位实际情况和候选人兴趣选择：
  1. 对希望转入 AI 的平台工程师，介绍平台如何支持训练与推理业务
  2. 对已有 AI 平台经验的人，介绍集群规模、负责范围和当前技术问题

**RL 系统岗 JOB-104（沈一舟，团队配置示例）：**

- 适用情境：团队组建期的高优先级岗位，本示例中负责人刚到任
- Junior 和 Senior 都可以看，leader 愿意培养人
- 但不能让团队倾斜，要混搭着推（不能只推 junior 或只推 senior）
- 本示例更关注相关背景和绩效；初级候选人同时看成长潜力
- 技术栈：veRL/OpenRLHF、训推一体、rollout 吞吐优化、reward server 工程化

**其他岗位（JOB-105/106/107）：** 尚未与用人经理对齐偏好，只按 JD 匹配 + 通用偏好判断；对齐后把口径补进本段。

## Step 1｜提取候选人画像

从简历中提取以下关键信息：

| 字段 | 要点 |
|------|------|
| 学历 | 学校档次（985/211/海外名校/普本）、专业相关度、本硕博、排名/GPA |
| 年龄/年限 | 毕业时间推算工龄，判断成长速度是否超出同年限平均 |
| 公司履历 | 大厂/大模型创业公司/小公司；每段待了多久；有无频繁跳槽或 gap |
| 主力语言 | Go / C++ / Python / Java — 决定方向归属 |
| 技术栈 | 核心框架和中间件（K8s/CUDA/Ray/NCCL/Docker 等） |
| 开发内容 | 自研、修改核心实现、集成或使用框架；记录具体工作，不仅贴标签 |
| Scope/规模 | 管了多少卡/核/QPS — 量化指标反映事情大小 |
| 角色 | 项目负责人 / 核心开发 / 参与者 |
| 底层系统岗位证据 | 细分方向；模型参数/卡规模；具体瓶颈与本人动作；吞吐/MFU/显存/稳定性等结果 |

## Step 2｜匹配岗位

将候选人核心技术方向与本次选定的岗位逐个比对。下表仅对应仓库中的示例岗位：

| 方向大类 | 典型技术栈 | 对应岗位 |
|----------|-----------|---------|
| 训练框架-预训练 | 先按算子/稳定性/多模/主训归类；再核验底层实现、主导程度、规模与量化结果 | JOB-101 |
| 推理引擎 | CUDA, C++, TensorRT, vLLM, SGLang, PD分离, KV Cache | JOB-102 |
| ML 平台 | Go, K8s, GPU调度, Ray, 弹性扩缩, Serving | JOB-103 |
| RL 系统 | 综合训推技术栈但亮点是 RL。Python, C++, RLHF框架, veRL | JOB-104 |
| 集群/IaaS | 资源调度, 裸金属, 混部, 利用率治理 | JOB-105 |
| 数据工具链 | Python, Ray, Spark, 数据Pipeline, Dataloader, Checkpoint | JOB-106 |
| 高性能网络 | C++, RDMA, NCCL, 通信优化 | JOB-107 |

**判断要点：**

- 找最佳匹配（经验直接对口）和次选匹配（可迁移）
- 区分"做过类似的事" vs "做过相邻的事" vs "方向不搭"

## Step 3｜按选定口径评估

下表是本仓库的“三点取两点”示例。正式任务使用用户已确认的评分标准；尚无评分标准时，先列岗位要求、对应证据和待确认项。

| 维度 | ✅ 满足 | ❌ 不满足 |
|------|---------|----------|
| 经验匹配 | 核心经验直接对口 JD 要求，或有明确可迁移路径 | 方向不搭，或只是"用过"而非"深度做过" |
| 年轻高潜 | 同年限下成长速度快：scope 大、晋升快、角色重 | 年限长但做的事浅，或成长轨迹平 |
| 学历 | 985/211/海外名校 + CS 相关专业 | 普本且专业不相关（除非经验极强可补） |

**打分对应：**

- 3 点全中 → ⭐ 强推荐
- 2 点 → ✅ 推荐
- 1.5 点（边界）→ ⚠️ 需 pre-talk 确认后决定
- ≤1 点 → ❌ 不推

某维度处于半满状态（如 scope 够大但晋升节奏平）可记 0.5 点，在结论里写清是哪半点、为什么。2.5 点按 ✅ 推荐处理，但要注明未达 ⭐ 的原因。

## Step 4｜输出结论

默认结论可采用以下结构；按本次任务增减字段，次选岗位和风险项没有依据时不凑内容：

```
## 候选人姓名 — [⭐/✅/⚠️/❌] 判断

| 维度 | 判断 |
|------|------|
| 经验匹配 | ... |
| 年轻高潜 | ... |
| 学历 | ... |

**最佳匹配岗位：** JOB-1XX（岗位名）— 匹配理由
**次选岗位：** ...
**风险/注意点：** level 是否够、薪资预期、稳定性、gap 等
**如果是 ⚠️：** pre-talk 需确认的问题清单
```

**考虑 JOB-101 时补充以下证据：**

> 全库匹配中，简历出现 Megatron、CUDA、千卡、MoE 等相关内容时，也检查是否属于预训练底层研发。证据不足时简要说明原因；仅筛其他指定岗位时，不必追加 JOB-101 专项报告。

```
**细分方向：** [P0 算子开发 / P0 训练稳定性 / P1 多模训练 / P1 主训 / 未归类]（可写一个主方向 + 一个次方向）
**预训练直接证据：** 项目、规模、具体问题、本人动作和结果；没有就明确写"简历未提供"
**深度判断：** 造轮子/深度改造/使用框架；主导/核心参与/普通参与
**关键缺口：** 需要 pre-talk 补证的点；不能用技术关键词自行补全
```

## 示例补充口径（加分/减分项）

**加分：**

- 有大模型公司直接相关团队经验
- 有开源贡献（K8s/PyTorch/vLLM/Ray 等）：按实际改动和岗位相关性判断；贡献规模较小但被明显夸大时列为待核实项
- 做过 0→1 项目且规模做大

**减分：**

- 频繁跳槽（连续 2 段以上 <1 年，或近 5 年 ≥3 家）。单次短任期不算减分项，列进 pre-talk 必问确认原因即可
- 中间有不可解释的 gap 或明显降级（大厂→小公司且非创业）
- 简历包装痕迹重（用词华丽但细节经不起问、开源项目实际贡献度低）
- 只有 Java 经验无 Go/C++（平台岗位适配性差）

## 特殊情况处理

- **真实候选人简历提到开源贡献** → 通过项目链接核实账号、改动和贡献，再决定是否加分；示例中的虚构账号不作为真实核验对象
- **无法联网核验开源贡献时** → 不要凭简历自述计入加分。改为在结论中输出「待核验项 + 具体核验方法 + 核验通过/不通过分别如何影响判断」，并标注本次结论为"开源未核验"状态
- **候选人方向不完全对口但背景很好** → 放 mapping 池，不急推，记录其 peer/组织信息
- **候选人适合多个岗位** → 列出首选+次选，pre-talk 时探意愿再定
- **底层系统岗候选人覆盖多个细分方向** → 先列证据最充分的主、次方向，其余作为补充；方向多不直接等于技术深度足够
- **候选人做过推理/后训练也做过预训练** → 只用预训练部分判断 JOB-101，并在 pre-talk 先确认下一份工作是否愿意继续做预训练
- **高阶候选人（总监/架构师级）** → 标注给团队 leader 主看
- **可迁移背景与直接匹配分开说明** → 从相邻平台方向转入时，说明可迁移经验和缺口；已经在 AI 平台工作的候选人，直接核对岗位职责，并围绕其关注点介绍工作内容

## Pre-talk 问题参考

按本次结论中的关键缺口选问，已有答案不重复问；技术核实、求职意向和招聘 mapping 可分开沟通。

| 问题 | 目的 |
|------|------|
| 看机会的原因和背景 | 判断动机、紧迫度 |
| 团队规模和分工是什么？哪些组织信息方便交流？ | 了解职责范围；有 mapping 需求时记录对方愿意分享的信息 |
| 现在手里的包（base+bonus+股票） | 判断薪资预期是否可控 |
| 本次都看了哪些公司 | 了解竞对、判断决策周期 |
| 最近的晋升、绩效和职责变化 | 结合组织背景理解本示例的成长维度 |
| 目前负责什么、带多少人、同级如何分工 | 补充本人职责和团队信息 |
| 简历空档期的情况是否方便介绍 | 澄清履历，避免直接推断原因 |

**暂不考虑机会的人：** 先确认是否愿意保持联系；对方愿意继续交流时，再了解职责和团队情况。

**JOB-101 可追加的问题：**

| 问题 | 目的 |
|------|------|
| 你做的是预训练、后训练还是推理？各自占比？下一份更想做哪块？ | 确认岗位边界与方向意愿 |
| 四个细分方向里哪一块最深？你本人负责到哪一层？ | 确定主方向，排除"都做过但都浅" |
| 挑一个最难的问题：规模、瓶颈、定位过程、你的改动、量化结果？ | 验证深度、scope 和个人贡献 |
| 是否处理过 Loss/Grad 异常、通信 hang、OOM 或性能回退？如何定位根因？ | 核验训练稳定性能力 |
| 是否亲自开发 CUDA/通信算子？具体算子、profiling 工具、收益？ | 核验算子开发而非调用经验 |
| 最早到岗时间？是否受竞业影响？ | 判断实际推进优先级 |

## 产物落盘

结论默认保存为 Markdown，便于后续查阅和跟进。用户只需要聊天结论时不保存。

- 路径：`推荐/<岗位编号>_<候选人>.md`（如 `推荐/JOB-101_李四.md`）；进 mapping 池不推的放 `推荐/mapping池_<候选人>.md`
- 内容就是 Step 4 的输出原文，不用另做加工
- `推荐/` 已被 `.gitignore` 忽略；若用户另指定路径，检查该路径是否被 Git 跟踪
- 用户明确说"只在这儿看看不用存"时才跳过

## 文件

- `jobs/` —— 岗位库，一岗一个 md，格式见 `jobs/README.md`
- `scripts/extract_resume.py` —— PDF 文本提取、页面渲染与 OCR；通过根目录 `./run pdf` 使用
- `examples/` —— 两组示例：输入简历 PDF + 经编辑整理的筛选结论
- `_tmp/` —— 临时文件
