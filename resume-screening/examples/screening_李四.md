## 开源贡献核验（⚠️ 本次未联网，以下为待核验项与核验方法）

按 SOP 特殊情况处理，开源贡献必须在出结论前实际核验。本次结论**未把开源计入正向加分**，仅作为一致性印证使用。需核验两项：

**① Megatron-LM：2 个 PR，修复 MoE 场景专家容量计算边界条件（自述已合并）**
- 项目含金量：**高**。NVIDIA 官方项目，且是 JOB-101 JD 点名的框架，PR 被合并意味着通过了官方 review。
- 但贡献粒度：**小**。2 个 PR + 边界条件 bugfix 属维护性改动，不等于"Megatron 核心贡献者"，不能当作主要筹码。
- 怎么核验：
  - GitHub 搜索 `repo:NVIDIA/Megatron-LM is:pr author:<候选人 handle>`，先确认 handle 与简历 `github.com/lisi-example` 一致
  - 看 PR 状态是否真为 merged（而非 closed），以及 diff 行数与改动文件——是改到 MoE 容量计算核心逻辑，还是只加了一个 if 判断/改了个断言
  - 看 review 往返轮次与 maintainer 评论——多轮技术讨论说明他确实理解这块代码，一次通过的 typo 级改动说明有限
  - 交叉验证：PR 提交时间是否落在星枢任期内、是否与简历所述 MoE 容量因子项目时间吻合

**② 个人项目 moe-bench：MoE 并行策略对比测试工具，约 240 star**
- 项目含金量：**中等偏上**。细分领域 benchmark 工具拿到 240 star 说明有真实需求，但 star 数本身不证明代码深度。
- 怎么核验：
  - Contributors 页看 commit 分布——他是否为 90%+ commit 的主要作者，还是 fork 别人的项目后挂名
  - Commit 历史时间跨度——是持续维护（多次迭代、响应 issue）还是一次性推上去吃早期流量
  - 用 star-history 看增长曲线是否自然（突然的垂直上涨需警惕）
  - Issue / PR 区是否有外部真实用户在用、他是否认真回复
  - README 是否包含真实实测数据与可复现脚本——若有，可直接与简历中 EP/容量因子的技术叙述交叉比对，是验证技术深度最省力的一手材料
- 若核验通过（本人主导 + 持续维护 + 有真实用户），这是**强加分**：说明他对 MoE 并行的理解足以抽象成通用工具，与 JOB-101 主训方向高度共振。
