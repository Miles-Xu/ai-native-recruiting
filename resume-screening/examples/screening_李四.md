# 李四：强推荐沟通 JOB-101

主要经历是大模型预训练框架的并行、显存与稳定性优化，与 JOB-101 相关。简历描述了 1536 卡、145B MoE 项目及对应改动和结果，主方向为 P1 主训，次方向为 P0 训练稳定性。算子开发有一项具体项目，是否满足团队当前需要还要进一步确认。

## JOB-101 项目证据

以下均为简历自述。

| 方向 | 规模与问题 | 本人工作 | 结果 |
|------|------------|----------|------|
| P1 主训 | 145B MoE、1536 卡 A800，专家负载不均产生长尾 | 作为主要负责人重构 EP 通信路径，重叠 All-to-All 与专家计算，并调整动态容量因子 | MFU 从 38.2% 至 46.5%，单次预训练周期缩短约 11 天 |
| P1 主训 | 激活显存开销 | 设计分层选择性重计算，调整并行配置 | 峰值显存下降 23%，吞吐额外提升 6% |
| P0 稳定性 | All-Reduce hang、grad norm spike、checkpoint straggler | 排查 NCCL 与 RDMA 驱动版本、归约顺序，改用异步分片保存 | 连续无故障训练时长从 4.7 天至 21 天以上 |
| P0 算子，补充证据 | fused RMSNorm + residual add 的访存瓶颈 | 用 Triton 实现融合算子，通过 Nsight Compute 调整 tile 与加载方式 | 单算子提速 2.3 倍，端到端吞吐贡献约 1.8% |
| 早期训练项目 | 7B/13B 模型、256 卡 | 调优 TP/PP，参与梯度累积与通信重叠 | 相比默认配置吞吐提升 19% |

**开发内容：** 包含框架源码修改、通信路径重构、显存策略设计和一个融合算子实现。MoE 吞吐项目明确标注主要负责人；其他项目的个人贡献比例需补充，不能仅凭“设计”“定位”等动词确定主导程度。

**方向与缺口：** P1 主训证据最完整；P0 稳定性有具体问题和处理描述。按本示例的算子要求，单个融合算子先作为补充证据，不直接认定为算子专长。简历未描述多模预训练项目。

**规模与范围：** 1536 卡和 145B 满足示例中的规模要求，但负责并行与显存方向不等于负责预训练全流程。

## 开源贡献待核验

本示例使用虚构账号，不联网验证，也不将开源自述计入加分。真实候选人可按以下方式核对：

| 简历自述 | 核验内容 |
|----------|----------|
| Megatron-LM 两个 PR 已合并，修复 MoE 专家容量边界条件 | 确认账号归属、PR 状态、具体改动、问题背景、测试及评审讨论，判断本人贡献和岗位相关性 |
| 个人项目 moe-bench，约 240 star | 查看代码来源、作者贡献、维护历史、基准方法、复现结果和使用反馈 |

PR 数量、代码行数、评审轮次或 star 数都不足以单独判断贡献深度。核实的改动和复现结果可补充项目证据；如果发现自述与实际不符，需要重新审视相关结论。
